# Ancestor-aware coin selection: coin-select vs Bitcoin Core

Generated by `python3 bench.py report`. Every package-quality number below is recomputed
by the harness from the fixture and the selected candidate ids, not taken from either
runner, so the two columns are scored by the same formula.

## Revisions and environment

- Bitcoin Core: `9be056a8a72b624dae9623b2f7bded92c2a21c91` (v31.1)
- coin-select: `e45bb58efef5752356d3299cfd545ca8059df4fb` (feature/lowest-fee-changeless: ancestor-aware selection on the delta-aware evaluator, with a dedicated LowestFeeChangeless metric)
- host: Linux-7.1.7-x86_64-with-glibc2.42 (24 cpus)
- compilers: g++ (GCC) 15.2.0 (-O3 -std=c++20); rustc 1.97.1 (8bab26f4f 2026-07-14) (release, codegen-units=1, lto=off, debug=true)
- Core patches applied: core-bench-hooks.patch (instrumentation only, see patches/README.md)
- search budget: 100000 (Core's compile-time `TOTAL_TRIES`; coin-select is given the same number of branch-and-bound rounds)
- timing: 2 warm-up run(s), 9 measured run(s), median reported

**The objectives are not identical.** Core's `SelectCoinsBnB` looks for the least-waste
selection whose effective value lands inside `[target, target + cost_of_change]`;
coin-select's `Changeless<LowestFee>` minimises the child transaction's fee over every
changeless selection. Runtime and node counts are therefore compared directly, while
solution quality is only ever compared through the shared metrics below.

## Objective cross-scores

Each engine's selection scored on **both** objectives by the harness. Core minimises the
`waste` column, coin-select minimises fee; each is expected to win its own column, so the
interesting cases are the ones where an engine also wins the other's. A selection whose
Core-accounted effective value falls below Core's target has no waste: Core's own
`RecalculateWaste` asserts that case away, so it is reported rather than scored.

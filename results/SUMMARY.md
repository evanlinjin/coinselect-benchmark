# Ancestor-aware coin selection: coin-select vs Bitcoin Core

Generated by `python3 bench.py report`, and overwritten on every run — edits here do not
survive. Every package-quality number below is recomputed by the harness from the fixture
and the selected candidate ids, not taken from either runner, so the two columns are
scored by the same formula.

This reports the **pinned** revision. The hand-written [`SUMMARY.md`](../SUMMARY.md) in the
repository root is a different document: what is being tried to move these numbers.

## Revisions and environment

- Bitcoin Core: `9be056a8a72b624dae9623b2f7bded92c2a21c91` (v31.1)
- coin-select: `e93d1f982c3d548613b0d1b5510f80967b2e057e` (PR #76: a second, ancestry-aware greedy seed, on top of PR #75's sparse per-candidate ancestor sets and PR #73's depth-first branch and bound with the changeless metrics removed)
- host: Linux-7.1.7-x86_64-with-glibc2.42 (24 cpus)
- compilers: g++ (GCC) 15.2.0 (-O3 -std=c++20); rustc 1.97.1 (8bab26f4f 2026-07-14) (release, codegen-units=1, lto=off, debug=true)
- Core patches applied: core-bench-hooks.patch (instrumentation only, see patches/README.md)
- search budget: 100000 (Core's compile-time `TOTAL_TRIES`; coin-select is given the same number of branch-and-bound rounds)
- timing: 2 warm-up run(s), 9 measured run(s), median reported

**The objectives are not identical.** Core takes the least-waste selection across its whole
algorithm portfolio and deliberately aims for a privacy-friendly change amount;
coin-select's `LowestFee` minimises the child transaction's long-term fee, with change at
the metric's discretion. Runtime and node counts are therefore compared directly, while
solution quality is only ever compared through the shared metrics below.

**`median time` is the one column here that is not reproducible.** Every other number in this report is deterministic — repeat the run and it comes back identical — but this is a median over fixtures whose own times span four orders of magnitude, so it moves with background load: three consecutive runs of the same binaries on the same machine gave 967, 968 and 1,228 us. Read it as an order of magnitude, and use `bench.py compare-revs` (interleaved, pinned to one core, minimum rather than median) to compare two revisions.

interesting cases are the ones where an engine also wins the other's. A selection whose
Core-accounted effective value falls below Core's target has no waste: Core's own
`RecalculateWaste` asserts that case away, so it is reported rather than scored.

## Verification

Every selection was re-derived from the fixture: each package reaches the target
feerate once its ancestor union is counted, each stays inside `max_weight`, and each
runner's own bump-fee figures match the harness's independent recomputation.

Known fee-model gaps, within tolerance:

- no_ancestry_1000/wallet/bitcoin-core: 20 sats short of the target feerate, within the 20 sats Core leaves unfunded for 0 legacy input(s)
- no_ancestry_2000/wallet/bitcoin-core: 20 sats short of the target feerate, within the 20 sats Core leaves unfunded for 0 legacy input(s)
- wallet_mixed_1000/wallet/bitcoin-core: 10 sats short of the target feerate, within the 10 sats Core leaves unfunded for 3 legacy input(s)
- wallet_mixed_2000/wallet/bitcoin-core: 20 sats short of the target feerate, within the 20 sats Core leaves unfunded for 6 legacy input(s)
